2026-06-01 — Three-level retrieval intent (specific / inbetween / global), medoid removed
==========================================================================================
WHAT
- Retrieval is now intent-driven, not corpus-size-first:
    specific  -> pgvector top-k over content_full
    inbetween -> skeleton (LLM picks ltree branches) for ANY corpus size
    global    -> corpus<=budget ? stuff-all : skeleton
  Reason: "summarise topic X" needs all of ONE topic, not the whole project, so it
  must focus (skeleton) even on a small corpus instead of blindly stuffing.
- intent="auto": free keyword pass (specific vs not) -> only on a hit, one cheap LLM
  call (_llm_classify_scope) splits inbetween vs global (fallback: inbetween).
- Removed the medoid strategy entirely (lossy). Skeleton planner failure now falls
  back to a budget-capped _stuff. Clusters are still computed (map UI), just not
  used for retrieval.
- Removed `scope` plumbing everywhere (router/grounded_answer/send_message/prefs/
  REPL); dropped preferences.default_scope; default_intent choices now
  (auto, specific, inbetween, global).
- Slash commands no longer force intent=global. Instead each carries a
  retrieval_keyword ("mockexam"/"deepsummary") that is appended to the *routing*
  query (new grounded_answer routing_query arg) so they always trip the keyword
  pass and reach the classifier — answer still grounded on the real query, so no
  text pollution. deepsummary outline + sections inject the keyword too.
- planner_max_tokens (added earlier) also powers the new classifier call.
- retrieval.md trace drops scope, shows the classified intent + chosen strategy.

WHY
- The old flow stuffed the whole corpus for any global-ish query on a small project,
  wasting context and ignoring topic focus. Three levels give a clean mental model
  and reuse the existing skeleton machinery for the middle case.

VERIFIED (live, 3-PDF test project)

- "summarise everything about word embeddings" -> skeleton (classifier: inbetween)
- "overview of the entire course material"      -> skeleton (global, corpus>budget)

2026-08-20 — Phase 1 step 3: db.py ported to SQLite, plus app/paths.py

WHAT
- app/paths.py (new): resolves data / cache / logs directories. Order:
  F7OWS_*_DIR env (what the Tauri shell will pass to both sidecars) -> ./devdata/
  when running from a source checkout -> OS conventions when frozen. Exposes
  db_path(), documents_dir(), runs_dir(), models_dir(); `python -m app.paths` prints them.
- app/db.py: asyncpg pool -> one aiosqlite connection per process. Loads
  sqlite-vec, sets pragmas (WAL, foreign_keys=ON, busy_timeout=5000,
  synchronous=NORMAL), runs migrate() on open, checkpoints the WAL on close.
  Keeps the names main.py/worker.py already import (create_pool / close_pool /
  get_pool / acquire), so neither file changed.
- Connection: a thin asyncpg-shaped adapter (fetch / fetchrow / fetchval /
  execute / executemany / transaction) so step 4 only rewrites SQL, not the
  Python around it. execute() returns the cursor so the ingest path can read
  lastrowid to link a chunk to its vector.
- embed.py now imports EMBED_DIM from app.migrations (1024). The 3072/1024
  mismatch flagged in step 2 is closed.
- .gitignore: backend/devdata/.

WHY (the two decisions)
- One connection per process, not a pool: SQLite serialises writes anyway, so a
  pool mostly buys threads that queue behind each other. Cross-process
  concurrency is WAL + busy_timeout, which is what actually matters here (web
  reads while the worker writes).
- acquire() holds an asyncio.Lock for its whole block. With a single shared
  connection two tasks could otherwise interleave statements, and a write from
  task B could land inside task A's open transaction. Verified first that no
  acquire() block in this codebase awaits anything slow (no LLM/network call is
  made while holding one), so serialising costs nothing.
- transaction() uses BEGIN IMMEDIATE, not BEGIN: a deferred transaction takes its
  write lock lazily, so two processes that both read then write deadlock instead
  of queueing.

TRAP AVOIDED (measured)
- Did not use sqlite3.Row. Its `in` operator iterates the row's VALUES, not its
  column names, so auth.py's `"openrouter_key" in row` would have quietly
  evaluated False and the user's BYOK key would never have loaded. app.db.Row is
  a dict subclass that also supports positional access, so row["x"], row[0],
  "x" in row and dict(row) all behave like asyncpg's Record.

VERIFIED (10 checks, on a scratch DB via the env override)
- env override respected; execute() exposes lastrowid; Row semantics incl. the
  `in` trap; fetchval returns None on no rows; executemany populates FTS via the
  trigger (5 chunks -> 5 fts rows); transaction() commits and rolls back; FK
  cascade from users wipes projects/documents/chunks/vectors/fts; 10 concurrent
  acquire() blocks with 0 interleaving; close_pool() checkpoints the WAL away.
- app.main / app.worker / app.db / app.paths / app.migrations / app.embed all import.
- created_at lands as ISO-8601 UTC ('2026-08-20T13:25:50.614Z').

- testsuite/config.py: RUNS_DIR follows the same resolution, so the driver reads
  the runs the server just wrote.
- app/config.py, .env, requirements.txt: the 5 BUCKET_* settings and boto3 gone.

WHY THESE CHOICES
- Storage root is data_dir(), NOT paths.documents_dir(). storage_key already
  begins with "documents/" (documents.py:71), so resolving against documents_dir()
  would have produced documents/documents/<...>. Keys stay verbatim -> zero
  migration for rows already in the DB. Fixed documents_dir()'s docstring, which
  claimed the key had no such prefix.
- Traces went to the CACHE dir, not the data dir the TODO line said. runs/ grows
  without bound and is regenerable; under data it would ride along in every
  backup of the user's real work.
- _runs_dir() is a function, not a module constant: paths.runs_dir() mkdirs, and
  trace.py is imported on every request path whether TRACE is on or off. As a
  constant it would have created directories at import time even with TRACE=0.

TRAP AVOIDED
- Keys are built from user-supplied filenames. A bucket flattens "../x" into a
  harmless key; a filesystem does not. _resolve() resolves the path and requires
  the data dir to be among its parents, which also catches drive letters
  (C:\...), absolute paths, and symlinks pointing out of the tree. Verified all
  5 shapes raise ValueError.
- Write-then-rename (.part -> final): the old bucket PUT was atomic, a plain
  write_bytes is not. A crash mid-write would otherwise leave a truncated PDF
  that parses to garbage on the next ingest.

  * placeholders() — SQLite has no array parameter, so `= ANY($1::uuid[])` has to
    be expanded into the SQL text.
  * descendants_of() / ancestors_of() — the ltree <@ and @> operators.
  * serialize_vector() — the float32 blob sqlite-vec both stores and queries with.
- migrations._NOW promoted to public NOW, re-exported from db.py: it is the

  drift apart, rows written by a default and rows written by a query stop
  comparing correctly — which is exactly what the sweep depends on.

- scripts/check_sqlite_port.py (new): 63 assertions, real PDF, only embed stubbed.

THE TRAP THAT ALMOST GOT THROUGH (has a regression test)
- ltree `<@` reads naturally as `LIKE 'prefix.%'`, and that is what the TODO line
  suggested. It is wrong here: chunk path labels are slugified to [a-z0-9_]
  (chunk.py:79) and `_` is a single-character wildcard in LIKE. `LIKE 'a_b.%'`
  also matches 'axb.leaf' — a different branch of the tree. Retrieval would have
  silently pulled chunks from the wrong section, with no error anywhere and
  nothing in the output to make it obvious.
  Everything uses GLOB instead: its metacharacters are * ? [ ], none of which a
  slugified label or a zero-padded message label can contain.
- Same operator, second half: `<@` includes the prefix row itself, which
  `GLOB 'p.*'` does not match. Hence the `col = ? OR col GLOB ? || '.*'` pair
  rather than just the GLOB.

OTHER DECISIONS
- Vector search is a brute-force scan with vec_distance_cosine() over a join, NOT
  sqlite-vec's `MATCH ... k = ?`. The KNN form cannot be combined with the
  project and source-selection joins, and exhaustive is what the schema was
  designed around anyway (the 50k-chunk estimate in migrations.py). Both callers
  (retrieval _specific, projection search) use the same shape, so there is one
  way this works rather than two.
- Chunk inserts are one row at a time inside the transaction, not executemany:
  the vector lives in chunk_vectors keyed by the chunk's integer `seq`, and
  lastrowid is the only way to learn a fresh seq. In-process, so it costs nothing.
- FTS5 MATCH takes a query *language*, not a literal. Free user text containing a
  quote, a `*`, or the word NEAR is a syntax error -> a 500 on the search
  endpoint. plainto_tsquery absorbed that for us; _fts_query() now does.
- conn.execute() returns a cursor, so the three places that parsed asyncpg's
  "UPDATE 3" status tag via result.split()[-1] now read cursor.rowcount.
- clear_studied tests json_extract(study_status,'$.state') IS NOT NULL rather
  than <> '{}': study_status is TEXT, so two equal JSON objects can still differ
  as strings (key order, whitespace).

ZERO-PADDING (the phase 1 item that is a behaviour change, not a syntax one)
- _next_child_path returned str(n+1). Both ltree and TEXT compare labels
  lexicographically, so '10' sorted before '2' and ORDER BY path scrambled any
  thread that reached ten siblings. Now f"{n+1:04d}". Easy to lose, because at
  the call site it looks like just another line to convert.

WHY POLLING IS FINE
- Redis could block until a job arrived; a table has to be polled. That is the
  one thing this trade actually costs. At 0.25s idle sleep the added latency is
  imperceptible next to the upload it follows, and an idle indexed SELECT is far
  too cheap to matter on a laptop. What it buys: no second server to install,
  supervise, or explain, and the queue lives inside the one file that "back up
  your data" already covers.

TWO BUGS THE HARNESS CAUGHT IN MY OWN CODE (both fixed)
- _MAX_ATTEMPTS ran jobs 4 times, not 3. _claim() SELECTs `attempts` and then
  UPDATEs it in the same transaction, so the value handed to run_job was the
  pre-increment one and the first run looked like attempt 0. _claim now returns
  `attempts + 1 AS attempt` — the count including this claim.
- run_worker() originally called create_pool()/close_pool() itself. That made the
  loop un-embeddable: cancelling it closed the shared connection out from under
  the caller, which is exactly what the test harness does (and what any future
  supervisor would do). The loop now assumes an open database; _serve() owns the
  process lifecycle. Better layering, not just a test fix.

DESIGN NOTES
- Claim is SELECT ... LIMIT 1 plus a guarded UPDATE inside one transaction.
  Only one worker is expected, but nothing stops a user launching a second copy
  of the app, and BEGIN IMMEDIATE + `WHERE state='queued'` makes the loser of
  that race see rowcount 0 and move on rather than run the job twice.
- Jobs are processed one at a time (ARQ had max_jobs=10). Simpler, and the writes
  serialise in SQLite anyway; _IDLE_SLEEP_SECONDS and the loop are trivial to
  raise later if batch ingest feels slow.
- Retries: 3 attempts with a 10s backoff, because the likely failure is a network
  blip mid-embed rather than a bad PDF. An unknown func name fails the job
  instead of resolving to an arbitrary attribute of the module — JOBS is both the
  dispatch table and the allowlist.
- finalize_project's _FINALIZE_MAX_ATTEMPTS ceiling is not "give up on the batch",
  it is "stop waiting and recompute anyway", so one document stuck mid-parse
  can't hold the project's map hostage forever. Documented it in place; the old
  comment there was an unanswered question about exactly this.

VERIFIED (38 assertions, scripts/check_job_queue.py, all passing)
