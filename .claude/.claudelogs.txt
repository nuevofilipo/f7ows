2026-05-31 — Fixed Docling parser to parse a real STEM PDF cleanly
=================================================================

First end-to-end run on a real PDF (test.pdf, ~75-80pp) surfaced several problems.
All fixed in app/ingest/parse.py:

1. Windows symlink crash on model download (WinError 1314). HF model caching tries
   to symlink, which needs admin/Developer Mode. Fix: set
   os.environ.setdefault("HF_HUB_DISABLE_SYMLINKS", "1") at module top (before any
   huggingface_hub import) so HF copies instead. Works now with no manual env var.

2. Garbled text (the big one). Docling's DEFAULT backend (docling-parse) mangled
   text on a PDF with custom font encoding: "Scattered" -> "Sca tt e r e d". Raw
   pypdfium2 extraction of the same page was clean, proving it was the backend, not
   the source PDF. Fix: pin the pypdfium2 backend
   (PdfFormatOption(backend=PyPdfiumDocumentBackend)). Output ~32K -> ~113K chars,
   text clean, full page coverage.

3. std::bad_alloc dropped ~10 pages during the preprocess/render stage (silent
   partial ingestion). Switching to the pypdfium2 backend made these disappear.
   Also hardened the contract: parse() now calls convert(raises_on_error=False),
   checks result.status, and RAISES a new ParseError on FAILURE / PARTIAL_SUCCESS
   unless allow_partial=True. Rationale: for RAG, silently ingesting part of a doc
   is a data-integrity bug — fail loud so the worker can mark the doc errored.

4. Reverted a bad earlier change: I'd switched the layout model to DOCLING_LAYOUT_V2
   with a comment blaming a torch "even kernels" error that was never actually
   observed (the only real failure was the symlink one). Back to Docling's default
   (Heron) layout. Lesson: don't encode speculation as fact in comments.

5. Test-harness Unicode crash: print(markdown[:1500]) died on the cp1252 console
   for a LaTeX arrow. Fix: sys.stdout.reconfigure(encoding="utf-8") in __main__
   (file write was already utf-8). Harness uses allow_partial=True so you can still
   eyeball output on partial conversions.

Process notes (why this run was slow/expensive): each full parse is ~3.5 min
(80pp, CPU, layout+table models), and I re-ran it several times to diagnose/verify.
A workspace hook also polluted my reads of files in backend/ with repeated
"file is being written concurrently" text, so inspecting test_output.md kept
failing and I retried multiple ways. Final on-disk parse.py is the pypdfium2
version (verified).

Known fidelity gaps (NOT bugs — deferred per PHASE4_PLAN_v2 §6): math is emitted as
plain text, not LaTeX (0 '$' delimiters) — Docling's do_formula_enrichment (a
separate CodeFormula model) is off by default; figures become '<!-- image -->'
placeholders — VLM/figure captioning is explicit future scope. Open question for the
user: enable formula enrichment now for LaTeX, or defer.

2026-05-31  parse.py: collapse beamer overlay duplicate slides
================================================================================
What:
- Added _dedupe_overlay_slides(markdown) to backend/app/ingest/parse.py and
  applied it to the export_to_markdown() output inside parse().
- It splits the Markdown into slide sections (each `## ` H2 = one slide title)
  and, for any run of CONSECUTIVE sections with the same heading, keeps only the
  last one. No-op for non-slide PDFs (no consecutive duplicate headings).

Why:
- A real STEM deck (RLHF lecture) produced every slide 2-4x in a row, once
  garbled and once clean. Root cause: the PDF is a LaTeX beamer deck. Beamer
  emits one physical PDF page per incremental reveal (\pause/\onslide/\uncover),
  so one logical slide = several near-identical pages, all faithfully extracted
  by Docling.
- The garbled-vs-clean split is Docling's formula enrichment being inconsistent
  across these near-identical pages: on partial-overlay pages the equation
  region often isn't classified as a formula and its glyphs are dumped as
  scattered plain text ("p ψ RL = p θ ..."); on the final fully-revealed page it
  is recognised and emitted as clean $$...$$.
- Keeping the LAST overlay in each run fixes both problems at once: in beamer
  build order the last page is the fully-revealed slide (a superset of the
  earlier overlays) AND the copy whose formulas Docling rendered as LaTeX.

Verification (against existing test_output.md, 30-slide RLHF deck):
- H2 headings 80 -> 56 (24 overlay duplicates dropped); 44,876 -> 30,852 chars.
- The garbled RLHF equation block is gone; the surviving copy is the clean
  $$\psi^{*} = \arg\max_{\psi} ...$$ version. Spot-checked the multi-overlay
  "Aligning LMs with RL" and "RL in 2 slides" sections too — last copy is the
  clean, complete one.

Note: the LaTeX extraction itself was already as good as Docling gets; the fix
is deduplication, not better formula parsing. Tradeoff: two genuinely-distinct
consecutive slides that happen to share a title would be merged (rare in beamer;
distinct same-title slides are normally non-adjacent).

2026-05-31  parse.py: move overlay dedup BEFORE the model pass (speed)
================================================================================
What:
- Added _strip_overlay_pages(pdf_bytes) -> pdf_bytes, called at the top of
  parse() before Docling runs. Uses pypdfium2 text extraction only (no ML, near
  instant) to detect beamer overlay build-ups and rebuild a trimmed PDF with
  only the final page of each run, so Docling's slow per-page models (layout,
  TableFormer, CodeFormula) run on ~1/3 the pages for a beamer deck.
- Decision rule (per user): directional token containment with slack. Drop page
  N if >= 90% of its tokens (multiset) reappear on page N+1 -> it's an earlier
  overlay of the same slide. Helpers: _page_tokens, _containment,
  _overlay_keeper_indices. Threshold const _OVERLAY_CONTAINMENT_THRESHOLD=0.90.
- Best-effort: any pypdfium2 error falls back to the original bytes (never blocks
  ingestion); returns original bytes unchanged when nothing is dropped.
- Kept the existing markdown-level _dedupe_overlay_slides as a cheap SAFETY NET
  for residual dupes; reworded its call-site comment to say so.

Why:
- Profiling discussion: the slow part of local parsing is 3 CPU ML models run
  per *page*. Beamer emits one physical page per \pause reveal, so a 30-slide
  deck can be 80+ pages -> we were paying model cost ~3x. The post-hoc markdown
  dedup (added earlier today) removed the duplicate *text* but only AFTER the
  models already ran. Stripping overlay pages up front removes the wasted compute
  itself.
- Beamer PDFs are born-digital VECTOR text (glyphs with codepoints+positions),
  so page text is extractable instantly with pypdfium2 -- no models needed just
  to compare pages. (The models are still needed for what they uniquely do:
  CodeFormula reconstructs equation LaTeX from glyphs that extract as scattered
  text; TableFormer recovers table grids. Those run on the surviving pages.)

Design note / accepted tradeoff:
- The subset rule can merge two genuinely-distinct adjacent slides if the earlier
  one's full text is ~contained in the later one. Rare for real decks; intended
  behavior for overlays. User chose "strict subset but ~90%, allow imperfection".

Verification (no source test.pdf present, so unit-tested the logic):
- _overlay_keeper_indices folds overlay runs to the final page; keeps distinct
  non-subset slides (containment 0.0); reflow of 1/12 tokens = 0.917 still drops;
  empty/title-only intermediate page folds in (containment 1.0).
- _strip_overlay_pages roundtrip: 4-page PDF of empty pages -> trimmed to 1 valid
  page. Fallback path returns original bytes on error.

Not done (flagged as separate optional wins): OCR is default-ON (do_ocr=True) but
useless on born-digital decks -- could disable for speed, but would break scanned
PDFs, so left as a conscious decision for later. GPU acceleration also pending.

2026-05-31  chunk.py: structure-aware Markdown chunker (Phase 4, step 3)
================================================================================
What:
- New sibling package backend/app/chunk/ (separate from app/ingest/, per user
  request) with __init__.py and chunk.py. Pure module: Markdown in,
  list[Chunk] out. No DB / network / embeddings (the worker persists).
- chunk(markdown, *, doc_slug) -> [Chunk]. Chunk = dataclass(chunk_index,
  content_full, content_sparse, path[ltree str], heading_trail, token_count).
- Added tiktoken>=0.7 to requirements.txt (installed 0.13 into venv). Token
  counts use o200k_base (matches text-embedding-3-large); falls back to a
  word-count*1.3 estimate if tiktoken is missing so chunking never hard-deps it.
- Three stages:
  1. _split_sections: walk the heading stack into heading-scoped sections.
     Slug labels resolved HERE with sibling dedup (Example -> example, example_2)
     so downstream is collision-free. ``` fences tracked so a '#' inside code
     isn't read as a heading. Solves the §6 ltree-slug open question.
  2. _atomize: split a section body into paragraph atoms on blank lines, but
     keep $$...$$ math blocks and ``` fences WHOLE -> an equation is an
     indivisible unit (per user's hard requirement).
  3. _pack: greedy 400-800 token packing. While a chunk is under MIN it keeps
     merging across sibling sections (coalesces tiny slides); once >= MIN it
     flushes on a MAX overflow OR a new section. A single atom > MAX (long
     equation) becomes its own oversized chunk -- never split.
- content_sparse: regex + stopword compression. Math spans stashed behind \x00n\x00
  placeholders before the prose pass (so a stopword strip can't touch LaTeX),
  restored after. Headings / table rows / block-math lines kept verbatim;
  prose/bullets keep bold, numbers, Capitalised terms and symbols, drop only
  lowercase stopwords. spaCy/TextRank deferred (documented upgrade lever).
- Manual harness: python -m app.chunk.chunk reads app/ingest/test_output.md and
  prints chunk count, token min/median/max, compression ratio, sample paths.

Why:
- Build-order step 3 of PHASE4_PLAN_v2. Keeping it pure + deterministic makes it
  unit-testable and keeps Docling/embedding concerns out of the chunker.

Design fix found via the harness (worth recording):
- v1 used a "never merge across the top-level (H1) heading" rule and set each
  chunk's path to the group's common-ancestor. On the test deck (parser promotes
  every slide to a bare H2, no H1) this degenerated: every slide looked like its
  own top-level -> 41 tiny chunks (median 51 tok), and common-ancestor of any
  merged flat slides collapses to the bare root, erasing ltree granularity.
- Fix: (a) coalesce sibling sections until MIN_TOKENS; (b) set path/trail to the
  section the chunk STARTS in (a specific leaf) instead of the common ancestor.
  Result on the deck: 41 -> 8 chunks, median 453 tok (in-band), specific paths.

Verification:
- Harness: 8 chunks, tokens min53/median453/max529, paths like
  test.dpo_direct_preference_optimization. 13% sparse reduction on THIS deck is
  expected-low (slides are already terse: mostly headings+bullets we keep);
  prose textbooks will compress far harder.
- Synthetic tests pass: a 900-term $$...$$ block stays in ONE 5415-token chunk
  (never split, allowed to exceed MAX); inline $a is to b$ survives the stopword
  pass intact; sibling '## Example' x2 -> example / example_2.
- Known cosmetic edge: a title-only H1 immediately followed by content gives the
  chunk the H1's path (its heading atom leads the chunk), shadowing the child's
  label. Accepted -- the chunk genuinely spans from the H1 into the child.

2026-05-31  chunk.py: derive the chunk-boundary heading level (pivot), not H1
================================================================================
What:
- Replaced the hard-coded "boundary = H1" assumption with a measured pivot level.
  New _pick_pivot(atoms) -> int | None and _pivot_key(); _pack now takes a pivot.
- "Depth" = heading STACK NESTING depth, not the Markdown heading number, so a
  deck of bare ## slides (no H1) is depth 1, exactly like a textbook's top
  chapters. Level-agnostic by construction.
- _pick_pivot: for each nesting depth present, group atoms into the contiguous
  sections that depth would yield and score the grouping by |median_section_size
  - target|, target = geomean(MIN,MAX) ~566. Closest depth wins. Fall back to
  flat (None) only when the best median is < MIN/2 (=200): every structural level
  over-segments (e.g. ~50-token slides). No headings -> None too.
- _pack(atoms, pivot): close a group when the atom crosses a pivot boundary OR
  (>=MIN and would exceed MAX). Boundary is the transition between CONSECUTIVE
  atoms' pivot keys (not vs the group's first atom) so a stub ancestor heading
  (bare '# Chapter 2', < _STUB_TOKENS=16) is absorbed into the next section
  instead of splitting on every paragraph. Flat mode (pivot=None) has no
  boundaries -> tiny slides coalesce to the band; equations still never split.

Why:
- User feedback: keying on H1 overfits, and this deck has NO H1 (parser promotes
  each slide to ##). Wanted a measure that's "not too coarse, not too granular,
  with a fallback to plain text". Pivot-by-median-closeness-to-target delivers
  that and is derived per-document.

Two bugs found + fixed during this change (via the harness):
1. First gate was median < MIN (400): rejected a textbook's good 360-token
   section level and went flat, producing chunks that crossed chapter
   boundaries. Loosened to MIN/2.
2. Comparing each atom's pivot key against the GROUP'S FIRST atom broke once a
   stub heading rode forward: the stub's key (the chapter) never matched any
   child section, so it split on every paragraph (133/260/388...). Fixed by
   comparing CONSECUTIVE atoms instead.

Verification (synthetic + real):
- Slide deck (test_output.md): pivot -> flat; 5 chunks, 542-793 tok (was 41 tiny
  with the old H1 rule, then 8). Compression 13% (expected-low for terse slides).
- Synthetic 3xH1 / 3xH2 / 2xH3 textbook: pivot -> depth 2 (sections); 9 chunks
  ~388 tok with clean book.chapter_0.section_0_1 paths; chapter heading absorbed
  into its first section (no stub chunks).
- 700-term $$...$$ block: stays in exactly 1 chunk in both flat and pivot modes.

2026-05-31  retrieval: Dynamic Sparse Router (step 9) — token-budget routing
================================================================================
What:
- New sibling package backend/app/retrieval/ with router.py exposing
  route(project_id, query, *, intent, scope, k, budget) -> RetrievalResult
  (strategy, context, chunks, token_count, meta). GATHERS context only; it does
  NOT call the answering LLM (chat layer's job later).
- New app/llm.py: thin async OpenRouter chat-completions helper complete(messages,
  model=...). config.py: added llm_base_url (default OpenRouter) + planner_model
  (default openai/gpt-4o-mini), both env-overridable. Reusable by future chat.
- Routing (PHASE4_PLAN_v2 §4):
    intent "specific"                 -> 1 pgvector top-k cosine over content_full
    intent "global", corpus<=budget   -> 2 brute stuff all content_sparse (ltree-ordered)
    intent "global", corpus>budget, topic -> 3 agentic ltree skeleton (LLM planner)
    intent "global", corpus>budget, all   -> 4 medoid sampling from clusters
  intent/scope default to "auto" keyword heuristics but are overridable (a slash
  command is unambiguously global). budget (default 15k) is a param so tests can
  force the large-corpus branches.
- Corpus size for the decision is estimated cheaply as SUM(length(content_sparse))
  /4 (chars->tokens) so we never load a huge corpus just to decide not to.
- Strategy details: (1) embed query, ORDER BY embedding <=> $q::halfvec LIMIT k,
  returns content_full. (2)/(4) _assemble() concatenates content_sparse blocks
  (each prefixed [ltree.path]) until the token budget, always keeping >=1 block.
  (3) fetch DISTINCT path ToC -> cheap LLM picks branches (JSON array, verbatim
  paths) -> fetch WHERE path <@ ANY($2::ltree[]); on any LLM/parse error it falls
  back to medoid sampling (meta.fellback_from="skeleton").

Why:
- Build-order step 9, final ingest/retrieval piece. Global queries embed poorly,
  so route-then-gather by token budget instead of expensive map-reduce; keeps
  cost low (sparse text, medoid sampling, cheap planner).

- specific: top-3 by cosine distance (0.456/0.513/0.523), all RLHF chunks. Good

- medoid (forced budget=0, scope=all): pulled a cluster medoid from `clusters`.
- skeleton (forced budget=0, topic): LLM planner SUCCEEDED (fellback_from=None),
  selected 3 relevant RLHF ltree branches from the ToC, then path <@ ANY(::ltree[])
  fetched them. Confirms the asyncpg ltree[] array cast works.
- Note: budget=0 in the test caps assembly to 1 block (it only forces the branch);
  real 15k budgets include all medoids/branches.
